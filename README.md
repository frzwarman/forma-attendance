# Buku Tamu — event check-in (Bawaslu)

A one-event guest book on the web, in Bahasa Indonesia. Attendees open the link on their own phone: a page with two buttons, *Registrasi* (the guest book, `/registrasi`) and *E-Vote* (`/vote`). On *E-Vote* they pick from the options an admin set (one, or up to the number the admin allows) and send their vote, once per phone; the page then thanks them with their picks and offers *Lanjut ke Registrasi*, as it does while no vote is open. On *Registrasi* an event slideshow opens first (once per browser session). They fill in one form (Nama, Nomor Telepon and E-mail, then the questions the admins set up in *Formulir*, by default Divisi, and an optional photo taken with the camera or a chosen image/PDF) and tap **Kirim**. The server records the check-in time, shown in WIB, and a thank-you popup confirms it; closing the popup shows the event information on the page: the event banner, a *Ikut polling di Mentimeter* button, the event rundown as page images shown one at a time (swipe or the arrows for the next and previous page), downloadable PDF materials, and the speakers, each opening their CV as page images in a popup; then *Kesan & Pesan*, a box where the attendee writes their impressions and messages for the organisers (sent under their check-in, as often as they like, up to 50), and at the very bottom the check-out card. Admins edit all of it in *Info acara* (see the admin guide); until they save, the page shows the rundown and CVs built into the site (`BUILT_IN_CONTENT` in `src/services/eventInfo.ts`, JPEGs in `public/rundown/` and `public/narasumber/` made with `swift scripts/pdf-to-jpg.swift file.pdf public/narasumber/name` on macOS). When leaving, attendees open the same link on the same phone, tap *Registrasi*, then *Check out sekarang*: the phone keeps a private check-out code from the check-in. *Selesai* on the check-out popup takes them back to the link page (or, while someone else is still checked in on that phone, keeps the page open for that check-out). The event has two sessions a day, so attendees check in again at each one: when an admin starts the next session (*Mulai Sesi 1* or *Mulai Sesi 2*), the attendee's page goes back to the form the next time it is opened or looked at, without checking anyone out; someone whose phone number or e-mail is already registered is welcomed without a second row, their row records the latest check-in and how many there were, and typing the same name gets a new check-out code for that visit. A *Hubungi panitia* WhatsApp button stays in the bottom-right corner when an organiser number is set. The opening slideshow starts with an animation (the Bawaslu logo reveal, looping while its slide shows), then the event banner, also animated and looping (from a phone video, encoded the same way), the speakers one per slide with only the name-and-photo part of their CV (a hand-made crop of page 1, `public/narasumber/<name>-profil.jpg`, sized in `SPEAKERS`), and the list of materials; the slides are defined in `src/features/intro/slides.ts`, and after check-in the page shows the banner alone. The animation came as a 29 MB GIF and is kept as video, about 250 KB (AV1 for Chrome, Android and Firefox; H.264 for Safari; a phone downloads one): its 4.5 KB first frame shows while the video downloads with the popup, fetched whole and played from memory because Cloudflare's static assets ignore the Range requests a video URL relies on (Safari stalled on the first frame). With reduced motion, or where autoplay is refused, its last frame shows as a picture instead. To replace it, encode the new one with the ffmpeg commands in `slides.ts`; never put the GIF itself on the page. Admins sign in at `/admin` to watch check-ins arrive, search them, export the full list to Excel or CSV, run a lucky draw, run the E-Vote and show its live count on a big monitor, and change the event name, texts, logo, background and colours. The default look is Bawaslu's, measured from the supplied key visual and https://www.bawaslu.go.id/id (see `assets/brand/README.md`).

Built with Expo Router on React Native Web (web only), TanStack Query, react-hook-form + zod, SheetJS for Excel, and Supabase (Postgres, Auth, Storage).

The interface uses Plus Jakarta Sans (loaded from Google Fonts with system fallbacks), the official Bawaslu logo on a white capsule over the navy key visual, a navy sidebar for the admin area, and inline SVG icons generated from lucide (`scripts/generate-icons.cjs`), so no icon library ships to the browser.

The previous workforce-attendance prototype is preserved on the `workforce-app` branch and the `workforce-app-final` tag.

## Run locally

First time on this project? Follow [GETTING_STARTED.md](GETTING_STARTED.md) for installing, connecting Supabase, creating the first admin and deploying.

Use Node 24 LTS (24.3+) or 22.13+.

```sh
npm ci
cp .env.example .env.local   # fill in both values from Supabase → Project Settings → API
npm run web
```

`.env.local` holds only the project URL and the publishable key; both are public client values and are embedded at build time. Never put the database password, CLI token, secret key or service-role key in an `EXPO_PUBLIC_` variable. Keep private CLI credentials in `supabase/.env.cli.local`, not in a root `.env.*` file: Expo's development server bundles every root file that starts with `.env` and only understands the standard names, so a file such as `.env.supabase.local` breaks `npm run web` with a 500 on the entry bundle.

```sh
npm run typecheck
npm run lint
npm test           # domain unit tests (theme, phone, time, validation, export) and the Google Sheet script
npm run db:test    # the real migrations in embedded Postgres (RLS, RPCs, storage policies)
npm run build:web  # production build into dist/
npm run weight     # public page weight gate (needs the dist/ build)
```

```sh
set -a; . ./supabase/.env.cli.local; set +a   # exports SUPABASE_DB_PASSWORD for the CLI without printing it
npm run db:plan    # dry run
npm run db:push
npm run db:status
```

What the migrations enforce: attendees can only call `guestbook_check_in` and `guestbook_check_out` (with the code their phone received; only a SHA-256 hash of it is stored, and repeating it is harmless) (validation, honeypot, one row per normalised phone number and per e-mail: a repeat check-in updates that row's latest check-in and count, takes the answers given this time (question by question; name, phone and e-mail stay as first given), clears its check-out, and returns a new check-out code only when the name typed is the stored one, since check-out answers with the name) and upload into `guestbook-uploads/checkins/`; only users listed in `guestbook_admins` can read check-ins, draw winners, update settings or read uploads. Settings are public so the page can render the theme. For E-Vote, attendees read the vote's options and can only call `guestbook_cast_ballot` (one ballot per phone ID and vote, checked against the vote's options and number of picks, not counted once the vote is closed or replaced); only admins save, close or count a vote, and nobody reads ballots directly.

**Owner checklist (Supabase dashboard, once):**

1. Authentication → Providers → Email: turn off *Allow new users to sign up*. (Even if left on, a self-registered user gets nothing: admin rights come only from the table below.)
2. Authentication → Users → *Add user* with the admin's e-mail and password.
3. SQL editor, with the admin's e-mail:

   ```sql
   insert into public.guestbook_admins (auth_user_id)
   select id from auth.users where lower(email) = lower('admin@example.com')
   on conflict do nothing
   returning auth_user_id;
   ```

   The result must show one row. If it shows none, the e-mail does not match an existing Auth user. To see who has admin rights:

   ```sql
   select u.email, a.auth_user_id is not null as admin
   from auth.users u left join public.guestbook_admins a on a.auth_user_id = u.id;
   ```

   An account that signs in without this grant sees "Akun ini belum menjadi admin" at `/admin`.

Repeat 2–3 for each admin. The two buckets (`guestbook-brand`, public; `guestbook-uploads`, private, 5 MB per file) are created by the migration.

## Deploy

```sh
npm run build:web
```

Publish `dist/` to any HTTPS static host (HTTPS is required for the camera). Set `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` wherever the build runs. The site is a single-page app, so `/admin` and its sub-pages need a fallback to `index.html`:

- Cloudflare Workers (the current deployment, `forma-attendance`): `wrangler.jsonc` in this repo serves `dist/` with `not_found_handling: "single-page-application"`. In Workers Builds use build command `npm run build` and deploy command `npx wrangler deploy`, and add the `EXPO_PUBLIC_` values under the build's variables, because they are embedded at build time.
- Netlify or Cloudflare Pages: a `_redirects` file in `dist/` containing `/*    /index.html   200`
- Vercel: `vercel.json` with `{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }`
- Firebase Hosting: `"rewrites": [{ "source": "**", "destination": "/index.html" }]`

Share the public link (the page with *Registrasi* and *E-Vote*, or a QR code of it) with attendees; keep `/admin` for the organisers. `/registrasi` and `/vote` open those two pages directly.

## Admin guide

The sidebar groups the pages by when they are used: *Saat acara* (Daftar Check-in, E-Vote, Hasil E-Vote, Undian), *Setelah acara* (Laporan) and *Pengaturan* (Formulir, Info acara, Tampilan); on a narrow screen they are one scrolling row with a rule between the groups.

- **Daftar Check-in** (`/admin`): running total, search by name, phone, e-mail or hotel room, newest first, a *Kamar* column with each attendee's hotel room, refreshed every 10 seconds. *Lihat berkas* opens an attendee's upload through a short-lived signed link. The list pages through PostgREST in blocks of 1,000, so a 4,000-row event loads completely.
- **Sesi**: the card above the tiles shows the session under way. Press *Mulai Sesi 1* or *Mulai Sesi 2* when that session really begins and confirm in the popup: check-ins from then on belong to it (and its sheet tab, named in the popup), and attendees who checked in earlier get the form again to check in for it; nobody is checked out. Nothing changes on its own, midnight included, so the first press of each day is *Mulai Sesi 1*; the card warns in red while a session from an earlier day is still running. The button of the session under way is disabled (a Sesi 1 carried over from an earlier day leaves *Mulai Sesi 1* open, for today's).
- **Check-out**: the Check-out column shows when each attendee left. *Check out* records it now for someone who cannot use their phone, *Batalkan* undoes a mistake, and *Check out semua* (with a confirmation) closes everyone still present at the end of the event. The *Sudah check-out* tile shows how many have left and how many are still present.
- **Ekspor Excel / Ekspor CSV**: one file with every check-in (WIB first and latest check-in times, the number of check-ins, the check-out time, all fields, and the prize and draw time of the earlier check-in draw, empty now that Undian draws from an uploaded list). Use the Excel export for Excel: it keeps phone numbers as text, whereas a CSV opened by double-click drops leading zeros. The CSV is UTF-8 with a BOM, and attendee text that looks like a formula is prefixed with an apostrophe.
- **Undian** (`/admin/undian`): a spin wheel over a list the admin uploads, so only the people meant to take part are on it. *Pilih file* (or a file dropped onto the dashed box) takes a CSV or Excel file whose first row names the columns: `Nama` (required) and, if wanted, `Kesan & Pesan`; any other column is refused with a message naming it, blank rows are skipped, at most 2,000 names. Uploading replaces the whole list, winners included (with a confirmation when there are winners). Type a prize name, press *Putar* in the hub: the database draws one name still on the wheel (`guestbook_wheel_spin`, so two admins cannot draw the same person), the wheel turns for five seconds and stops on it, and a panel over the wheel shows the name, the prize and the person's Kesan & Pesan when the file had that column; *Lanjut* takes the name off the wheel. With more than 80 names the labels are hidden and only the colours stay. *Layar penuh* fills the screen with the wheel, Putar and the panel (Esc goes back). *Peserta di roda* lists everyone still on the wheel with their Kesan & Pesan; *Ubah* corrects a name or message (a name is required, up to 120 characters; a message up to 2,000), *Hapus* (after a confirmation) takes a name off the list for good, e.g. someone who left. The winners are listed below with prize, time and note; *Kembalikan ke roda* puts a no-show back. With reduced motion the panel opens at once, without the turn.
- **E-Vote** (`/admin/evote`): *Judul* and *Subjudul* (up to 120 and 200 characters; empty keeps "Hasil E-Vote" on the monitor, "E-Vote" on the attendee's page and the pick instruction under them), the options attendees vote on at `/vote` (2 to 20, each up to 120 characters) and how many each person may pick (*Boleh pilih*, from 1 up to the number of options). Changing only the title or subtitle keeps the vote and its count. *Simpan & buka voting* opens the vote and *Tutup voting* stops new votes, keeping the count. Saving the same options, in the same order, with the same number of picks opens the same vote again; any change starts a new vote counted from zero, in which every phone can vote again (with a confirmation first when the vote under way has votes). *Reset hitungan* (beside *Tutup voting*, after a confirmation) starts the same vote again from zero, with the same options, number of picks and open or closed state: every phone can vote again, also one that voted, the earlier votes stay in the database but no longer count, and the sheet's `E-Vote` tab is emptied. Votes are anonymous and once per phone: the phone keeps a random ID in its browser storage, so someone could vote again from a private window, which is fine for questions like the seating layout but not for anything binding. Earlier votes stay in the database.
- **Laporan** (`/admin/laporan`): the event's story for the organisers, live from the database and printable (*Cetak / simpan PDF* hides the sidebar and the controls and prints every page). One set of filters drives everything: the days (*Seluruh acara*, *Minggu terakhir* before the last check-in, or *Pilih tanggal*, two dropdowns of the app's own (`src/components/Dropdown.tsx`, keyboard and mouse) listing only the days that have check-ins; attendees count by the WIB day of their first check-in) and a division, chosen by clicking its bar in *Peserta per Divisi* and shown as a chip with *Hapus filter*. The page opens with *Kesimpulan*, the conclusion written from the numbers: a headline (attendance, days and check-ins) and one fact per topic (the peak day, the largest division, the busiest session once the sheet is loaded, the vote's leading option, messages, winners), the key part of each in bold, then the tiles (unique attendees, every check-in with the average per person, event days, check-outs, hotel rooms, uploads). Trial check-ins never count: the demo seed's `@example.com` rows and names that are, as whole words, test, tes, testing, uji, coba, percobaan, contoh, dummy or demo ("Peserta Uji 9276"); the filter line says how many were left out. then the charts: *Peserta baru per hari* and *Jam kedatangan* as column charts (the peak in red, every column readable on hover or keyboard focus), *Kehadiran per sesi* (drop the Google Sheet's `Check-in` tab export, CSV or Excel, onto the page: it holds every visit with its Sesi, so this is the exact count and number of people per session, read in the browser and kept nowhere), *Peserta per Divisi* (clickable bars), *Undian* (the wheel's winners), *Jawaban formulir* (each extra question with its answer counts, spellings differing only in case or spacing grouped, the top 10 and "Lainnya"), *E-Vote* (a vote with fewer than 10 voters counts as a trial and is hidden behind *Tampilkan uji coba*; the latest real vote shows first, since a reset makes a new poll and the real count is the last one people voted in; the real votes are chips to switch between; a donut for up to four options, bars beyond), and *Kesan & Pesan* (the messages from the attendee page and the answers to the form's Kesan & Pesan questions, searchable, with *Sembunyikan nama* for printing).
- **Hasil E-Vote** (`/admin/hasil-evote`): the count of the vote under way under its title and subtitle, refreshed every 2 seconds, without the settings: for each option, in the admin's order, how many phones picked it and their share of the phones that voted (with several picks allowed the shares add up to more than 100%). The rows size themselves to the stage so every option fits, two columns past 10 options. *Layar penuh* fills the screen with it for a big monitor; Esc goes back.
- **Formulir** (`/admin/formulir`): the questions on the check-in form after Nama, Nomor Telepon and E-mail (those three are fixed: they recognise someone checking in again). Admins add questions (Teks singkat, Teks panjang, or Pilihan with one option per line), make them required, give each a placeholder (the greyed example in the empty box, or the empty choice of a Pilihan list; Divisi and Nomor Kamar Hotel show their built-in example while none is set), rename, reorder and remove them, saved in `guestbook_settings.form_fields`; *Pakai formulir bawaan* restores the default (Divisi); *Kembalikan Nomor Kamar Hotel* adds the hotel room question back. Divisi and the room keep their own columns; other answers are stored in `guestbook_checkins.answers` under the question's label, shown under each attendee in the list, searchable, and exported as one column per question after Nomor Kamar Hotel. Answers to a question removed or renamed later stay in the database and the export.
- **Info acara** (`/admin/acara`): the Mentimeter participation link (only `https://` links on menti.com or mentimeter.com), the rundown, the speakers and the PDF materials, saved in `guestbook_settings.event_content` and shown on every phone the next time the page opens. A rundown or CV is uploaded as a PDF (up to 20 MB) and the admin's browser turns each page into a 1240 px JPEG with pdf.js (loaded only on this tab, never on the attendee page) before uploading it to the public `guestbook-event` bucket. Each speaker can also get a profile picture (the name-and-photo part shown in the opening popup; without one the popup shows the first CV page). Speakers and materials can be renamed, reordered and removed; *Pakai data contoh* brings back the built-in content. Replaced or removed files stay in the bucket. Two admins saving at once: the last save wins.
- **Tampilan**: event name, welcome text (on the registration form; the link page at `/` shows the event name alone), organiser WhatsApp number (shows the *Hubungi panitia* WhatsApp button in the bottom-right corner of the public page), logo, background image and four colours (accent, background, surface, text), with a live preview and a one-tap Bawaslu preset. Uploaded images are resized in the browser (logo 1200 px, background 1920 px).

## Google Sheet

Every check-in can be copied to a Google Spreadsheet within a few seconds. The sheet is a log: a new row for every check-in, so someone who checks in three times has three rows, numbered by *Check-in ke-* and each with that visit's time (the database still keeps one row per person and counts the visits). A check-out or prize updates the row of the latest visit; columns are the export's, plus `ID` (`20261103000000_guestbook_sheet_sync.sql` and `scripts/google-sheet/Code.gs`). The database sends the changes in the background after saving; a check-in never waits for Google or fails because of it, but a send that fails (Google down) is not retried: the admin export stays the complete record, and the resend below fills the gaps.

1. Create the spreadsheet, then *Extensions → Apps Script*. Replace the contents of `Code.gs` with `scripts/google-sheet/Code.gs` and save.
2. *Project Settings* (gear) *→ Script Properties → Add script property*: `SECRET`, with a long random value (for example the output of `openssl rand -hex 24`).
3. *Deploy → New deployment*, type *Web app*, *Execute as: Me*, *Who has access: Anyone* (the database cannot sign in to Google; the secret keeps others out). Authorise, and copy the *Web app URL* (it ends in `/exec`).
4. Apply the migration (`npm run db:push`), then in the Supabase dashboard's SQL Editor save the URL and the same secret, and send the check-ins made so far:

   ```sql
   insert into private.guestbook_sheet (url, secret)
   values ('https://script.google.com/macros/s/.../exec', 'the same secret')
   on conflict (id) do update set url = excluded.url, secret = excluded.secret;
   select private.guestbook_sheet_resend();
   ```

Kesan & Pesan messages go to a `Kesan & Pesan` tab, a row per message with the sender's name, phone number, e-mail and Divisi. E-Vote votes go to an `E-Vote` tab, a row per vote with only its time (WIB) and picks (`Round table, U-shape` when several are allowed), no name; a TYPE LAYOUT answer moved from the form shows when its attendee last checked in. Votes go in batches: every 10 seconds the database job `guestbook-sheet-votes` (pg_cron) sends the votes cast since its last run, 100 per request, so a whole room voting at once stays well under Google's limit of 30 requests running at a time per account; a vote's row appears within about 10–20 seconds (Hasil E-Vote counts at once). The vote's code, which ties to no phone or person, is in a hidden column so a resend updates the row instead of repeating it. *Reset hitungan* empties the tab (its header stays), and a resend sends only the votes of the count under way. Publish the updated script (below) before applying `20261113000000_guestbook_evote_sheet.sql`: the migration sends the votes cast so far, which an older script ignores (`select private.guestbook_sheet_resend();` sends them again). The rows appear in a `Check-in` tab (every check-in) and in a tab per session, named in the row's `Sesi` column after the WIB day the session started and its name, such as `02-11-2026 Sesi 2`, created when the session's first check-in arrives. Sessions start when an admin presses *Mulai Sesi 1* or *Mulai Sesi 2* and run until the next, so a check-in after midnight still goes to the evening's `Sesi 2` tab until *Mulai Sesi 1* is pressed. After applying `20261109000000_guestbook_sessions.sql`, publish the updated script (below): until then the old script keeps splitting the tabs at 12:00. For 02-11-2026, when Sesi 1 ran past 12:00, run `repairSesi1On02Nov` once from the Apps Script editor after publishing the script and applying `20261110000000_guestbook_sesi1_continues.sql`, and before *Mulai Sesi 2* is pressed that day: it moves the day's visits from the `02-11-2026 Sesi 2` tab to `02-11-2026 Sesi 1`, sets their Sesi there and on the `Check-in` tab, clears the morning visits' 12:00 check-out and deletes the `02-11-2026 Sesi 2` tab (*File → Version history* brings anything back); running it again changes nothing. Someone who comes to both sessions is in both tabs. If they do not, `select status_code, error_msg, created from net._http_response order by created desc limit 5;` shows the latest sends (302 is normal: Apps Script answers with a redirect after writing; a timeout only means the script took longer than 30 seconds to answer). The script's *Executions* page (Apps Script, left bar) lists every request with its duration and any error. *Check out semua* and a resend send 100 people a request, all at once; the script takes them one at a time, each tab read and written in one go, so a request takes seconds and the next one waits its turn (up to 5 minutes). `select private.guestbook_sheet_resend();` sends everything again at any time; rows already in the sheet are updated rather than repeated, but since the database keeps only each person's first and latest check-in, a resend cannot rebuild earlier visits' rows. `delete from private.guestbook_sheet;` stops the copying. After changing the script, publish it with *Deploy → Manage deployments → Edit → New version* so the URL stays the same. Anyone the spreadsheet is shared with sees attendees' names, phone numbers and e-mails.

## Keeping the free database running

Supabase pauses a Free Plan project after about a week without user traffic (a few requests a day are enough to prevent it; a paused project is restored from the dashboard with its data). `.github/workflows/keep-alive.yml` reads the public settings row once a day through the REST API. It needs two repository secrets (GitHub → Settings → Secrets and variables → Actions): `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`, the same public values as `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Run it once by hand (Actions → Keep Supabase awake → Run workflow) to check the secrets. GitHub turns scheduled workflows off after 60 days without a commit and mails a warning first; a commit turns them back on. Delete the workflow when the project may pause. Paid plans are never paused.

## Data and privacy

Exports contain personal data; store and share them accordingly. After the event, delete the data from the Supabase SQL editor and empty the `guestbook-uploads` bucket in Storage:

```sql
delete from public.guestbook_draw_winners;
delete from public.guestbook_checkins;
delete from public.guestbook_wheel_entries;  -- Undian's uploaded list and its winners
select cron.unschedule('guestbook-sheet-votes');  -- stops copying E-Vote votes to the sheet
```

Attendee images are compressed to a 1600 px JPEG before upload and PDFs are capped at 5 MB, so 4,000 uploads stay around 1–2 GB. The free Supabase plan includes 1 GB of storage; upgrade if most attendees are expected to upload.

## Limitations

- One event at a time; re-theming replaces the previous look, history is not kept.
- Spam protection is a hidden honeypot only; add a captcha if abuse appears.
- Attendee uploads that fail before the check-in RPC are left in the bucket; clear them with the post-event cleanup.
- *Ambil foto* needs HTTPS and camera permission; when the camera is denied or missing the form explains it and *Pilih berkas* still works.
- `npm audit` reports advisories in `node-forge`, used only by Expo's build tooling.
